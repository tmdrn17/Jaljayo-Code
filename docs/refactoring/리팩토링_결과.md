- **기준:** `코딩스타일.md` 1~11번 (12번 "개선해 볼 점"은 제외)
- **범위**
  - 1차 (형식·이름·캡슐화, 1~7절): `original` 커밋(`bf227ba`) → S7 커밋(`8670bc2`)

## 4. 모든 스크립트에 공통으로 적용한 것

- 여는 중괄호를 다음 줄로, 들여쓰기 공백 4칸
- bool 부정은 `!` 대신 `== false`
- 필드 이름: private은 camelCase, public은 PascalCase, bool은 `is`/`can`/`has`
- public 필드를 `[SerializeField] private` 또는 `{ get; private set; }` 프로퍼티로 바꿈. 값 변경은 메서드로만 함
- 태그·씬 이름·버튼 이름 문자열과 숫자 값을 `const`로 모음
- 안 쓰는 `using`, 빈 `Start`/`Update`, 주석 처리된 옛 코드, 디버깅용 `Debug.Log`/`print` 삭제
- 클래스 맨 위에 역할을 한 줄 한국어 주석으로 적음. 깨진 CP949 주석은 UTF-8로 다시 씀
- LINQ(`SequenceEqual`)는 `for` 비교로 바꿈
- 필드 이름을 바꾼 곳은 씬·프리팹 YAML 키와 프리팹 오버라이드(`propertyPath`)도 같이 바꿔 인스펙터 값을 유지함

##### 5.1.1.1. 제네릭 `instance`를 찾고 중복·종료를 처리

- `Instance`: 처음 부를 때 `FindObjectOfType<T>()`로 찾고, 없으면 경고 로그를 남김
- 중복된 오브젝트는 파괴하고, 게임 종료 중에는 null을 돌려줌

**이전**
```csharp
    private static GameManager GMinstance;
    // ...
                GMinstance = FindObjectOfType(typeof(GameManager)) as GameManager;
                if (GMinstance == null)
                {
                    Debug.Log("싱글톤 오브젝트가 없습니다.");
                }
    // ...
        else if (GMinstance != this)
        {
            Destroy(gameObject);
        }
```
**이후**
```csharp
    private static T instance;
    // ...
                instance = FindObjectOfType<T>();
                if (instance == null)
                {
                    Debug.LogWarning($"[{typeof(T).Name}] 씬에 싱글톤 오브젝트가 없습니다.");
                }
    // ...
        else if (instance != this)
        {
            Destroy(gameObject);
            return;
        }
```

## 7. 작업 방식과 지표

### 7-1. AI를 사용한 이유

이번 리팩토링은 새 기능 추가, 업데이트, 버그 수정이 아닙니다. **과거 미숙했던 실력으로 작성한 코드를, 지금의 코딩 스타일과 새로 익힌 지식에 맞춰 바꾸기만 한 작업**입니다.

- **게임 동작은 바꾸지 않았습니다.** 수치, 타이밍, 판정, 씬 흐름, 세이브 형식은 그대로 두고 구조와 표현만 바꿨습니다. 버그로 보이는 곳도 고치지 않고 `// TODO(리팩토링):`로 표시만 했습니다.
- **바꾸는 기준이 이미 문서로 정해져 있었습니다.** `코딩스타일.md`에 이름 규칙, 형식, 캡슐화, 쓰는 문법과 쓰지 않는 문법을 정리해 두었습니다. 그래서 작업은 판단보다 기준을 적용하는 일에 가까웠습니다.

### 8.2. 바뀐 공용 API
- **`GameSession`** (static, 새 파일): HP·코인 값을 Health·Score·TotalScore에서 옮김. 값이 바뀌면 `OnHpChanged`·`OnCoinChanged`·`OnTotalCoinChanged`를 알린다. 표시 컴포넌트는 구독만 한다.
- **`GameManager`**: `CollectCoin()`, `GameOver()`(실패 씬 한 번만), `ResetForNewGame()`, `MoveCharacter`·`MovePlayer`, `EnterPuzzle`·`ExitPuzzle`·`UnlockMove`, `IsMoveLocked`. `Player.IsMove`·`SetMove`는 삭제.
- **`SaveManager`**: `TryLoadData()`(bool), `MarkLoadedFromSave(Vector3)`. 저장 필드 이름은 그대로.
- **약속 API (N2에서 확인):** `Button.Activate()`, `AnswerArea.PlaceStatue(Statue)`, `Statue.Kind`·`Value`, `Stage2UI.ChangePoint(int)`, `Stage2UI.ShowQuest(int)`(그대로).
- **Boss 패턴:** 필드를 `jumpAttack`·`yellAttack`·`strikeAttack`으로 묶었다. 추상 부모 `BossAttack`이 "애니메이션 → 대기 → 공격 → 쿨타임" 흐름을 정하고, 자식 3개(`LampDropAttack`, `FileFireAttack`, `TileStrikeAttack`)가 `Attack()`만 채운다.
- **`OXQuiz`**: `questions`·`answers` 배열 두 개 → `quizItems`(`QuizItem` 배열, 질문·정답 쌍). `answerIndex`·`questionIndex` → `currentIndex`.
- **`SecondFloorManager`**: Update 폴링 → `OnMissionCleared` 이벤트.
- **이벤트로 바꾼 곳 (R8):** `ColorBoxAnswer.OnWrongSequence`(ColorBox가 구독), `DoorAnimation`·`LastDoor`는 Update에서 플래그를 보던 것을 `OpenDoor()` 호출로 바꿈. OXQuiz 목숨 표시는 값이 바뀔 때만 갱신.
- **모든 파일에 공통으로 적용한 것**
  - 씬 이름·태그 문자열을 `SceneNames`·`Tags` 상수로 바꿈 (R1)
  - `tag ==` 비교를 `CompareTag`로 바꿈 (R2)
  - 경고 로그에 `[{nameof(클래스)}]`와 대상 오브젝트를 붙임 (R3)
  - 조정 값 `const`는 `[SerializeField]`로, 배열 길이를 베낀 상수는 `.Length`·`.Count`로, 다른 클래스 값을 베낀 상수는 원래 값 참조(`Boss.MaxHp`, `GameManager.HasAllPapers` 등)로 바꿈 (R9)
- 스크립트별 이전·이후 코드는 8.9절에 있습니다.

###### 8.9.3.1.1. 공격 패턴 부모 클래스와 템플릿 메서드 `Run`

- 보스 패턴 셋(`Jump`, `Yell`, `Strike`)이 모두 같은 흐름이라 부모로 묶음 (R10)
  - 흐름: 애니메이션 → 공격 전 대기 → 공격 → 쿨타임
- `Run(Boss)`이 흐름을 정하고, 자식은 `TriggerHash`와 `Attack()`만 정함 (템플릿 메서드)
- 패턴이 쓰는 프리팹·위치·시간 값은 각 패턴이 직접 가짐 (`[System.Serializable]`, `attackDelay`, `cooldown`)

**이후**
```csharp
[System.Serializable]
public abstract class BossAttack
{
    [SerializeField] private float attackDelay = 0.5f;
    [SerializeField] private float cooldown = 3f;

    /// <summary>패턴 시작 때 보스 애니메이터에 보낼 트리거</summary>
    protected abstract int TriggerHash { get; }

    public IEnumerator Run(Boss owner)
    {
        // 1. 애니메이션
        owner.PlayTrigger(TriggerHash);

        // 2. 공격 전 대기
        yield return new WaitForSeconds(attackDelay);

        // 3. 공격
        yield return owner.StartCoroutine(Attack());

        // 4. 쿨타임
        yield return new WaitForSeconds(cooldown);
    }

    protected abstract IEnumerator Attack();
}
```

##### 8.9.3.2. `BossAttacks/LampDropAttack.cs` (새 파일)

[System.Serializable]
public class LampDropAttack : BossAttack
{
    private static readonly int JumpHash = Animator.StringToHash("Jump");
    private static readonly Quaternion LampRotation = Quaternion.Euler(0f, -90.0f, 180f);

    [SerializeField] private float dropForce;
    [SerializeField] private GameObject lampPrefab;
    [SerializeField] private Transform[] lampPoints;

    protected override int TriggerHash => JumpHash;

    protected override IEnumerator Attack()
    {
        for (int i = 0; i < lampPoints.Length; i++)
        {
            GameObject lamp = Object.Instantiate(lampPrefab, lampPoints[i].position, LampRotation);
            lamp.GetComponent<Rigidbody>().velocity = Vector3.down * dropForce;
        }

        yield break;
    }
}

## 9. 고민과 선택

주요 구조 선택의 이유를 세션 노트, 스타일 가이드, 원본 소스에서 확인해 정리했습니다. 근거의 종류는 아래처럼 표시합니다.

- **기록됨:** 세션 노트에 이유가 남아 있음
- **규칙 근거:** 이유가 따로 적혀 있지 않고, 스타일 가이드(`.claude/skills/jaljayo-refactor/style.md`) 규칙을 따름
- **작성자 보완:** 기록이 없어 작성자가 직접 채워야 함

### 9.1. `SingletonBase<T>` (기록됨)

- **이유:** `Score`, `TotalScore`, `Health` 같은 UI 오브젝트는 꺼진 Canvas 위에 있거나 씬마다 여러 개 있습니다. `FindObjectOfType`로는 꺼진 오브젝트를 찾지 못하고, 단순 싱글톤으로 바꾸면 중복 파괴 때문에 UI가 사라집니다. 그래서 싱글톤은 씬을 넘어 하나만 있어야 하는 매니저(`GameManager`, `SaveManager`)에만 쓰고, UI 값은 static으로 남겼습니다 (5.1.4.2).
- **구현:** 처음 부를 때 찾고, 중복은 파괴하고, 종료 중에는 null을 돌려줍니다. 자식은 `Awake` 대신 `OnInitialize()`를 override합니다.
- **2차에서 이어진 선택:** UI에 흩어져 있던 static 값을 `GameSession`으로 옮기고, UI는 이벤트를 구독해 표시만 하게 했습니다 (8.2). 싱글톤을 쓰는 범위는 1차와 같습니다.
- **출처:** `notes/S1.md` 13행, `style.md` 5절
- **비교한 대안:** 작성자 보완 (씬별 static 필드, ScriptableObject, DI 컨테이너와 비교한 기록 없음)

### 9.2. `PingPongMover` 상속 (기록됨 + 규칙 근거)

- **이유:** `MoveFloor`와 `Spike`가 한 축을 왕복하는 같은 코드를 가지고 있었습니다. 별도 컴포넌트로 붙이면 씬에 저장된 인스펙터 값(`distance`, `moveSpeed`, `turnSwitch`)이 새 컴포넌트로 옮겨지지 않으므로, 부모 클래스로 묶어 키를 그대로 유지했습니다.
- **규칙 근거:** `style.md` "상속은 얕게, 공통 흐름은 부모, 자식은 override(템플릿 메서드)", `sessions.md` "묶기 애매하면 각자 정리"
- **출처:** `notes/S3.md` 10·27행, M3 합치기
- **비교한 대안:** 작성자 보완 (컴포넌트 공유, 인터페이스와 비교한 기록 없음)

### 9.3. enum + switch, 그리고 보스 패턴의 상속 전환 (규칙 근거 + 기록됨)

- **1차:** 태그 문자열로 나누던 움직임 종류를 enum으로 바꿨습니다 (`Spike`의 `SpikeMove`, `MoveFloor`의 `FloorMove`). 보스 공격 패턴도 enum + switch, 쿨타임은 코루틴으로 정리했습니다. 원래 있던 안쪽 enum `ColorType`은 최상위 `ColorKind`로 옮겼습니다.
  - **규칙 근거:** `style.md` 상태 관리 "enum + switch 또는 간단한 상태 머신"
  - **값 순서를 지킨 이유:** enum은 씬에 숫자로 저장되므로, 순서를 바꾸면 저장된 값이 다른 항목을 가리킵니다. 그래서 `ColorKind`는 원래 순서(White, Red)를 유지했습니다 (M3).
- **2차:** 보스 패턴만 enum + switch에서 상속(`BossAttack` + 자식 3개)으로 바꿨습니다.
  - **이유 (기록됨, plan-2nd R10):** `Boss`가 모든 패턴의 데이터(전등 위치, 서류 프리팹, 타일 등)를 들고 있었고, "애니메이션 → 대기 → 공격 → 쿨타임" 흐름이 패턴마다 흩어져 있었습니다. 부모가 흐름을 정하고(템플릿 메서드) 각 패턴이 자기 데이터와 `Attack()`만 가지게 했습니다. 새 패턴을 추가할 때 `Boss`를 고치지 않아도 됩니다.
  - 나머지 enum은 종류에 따라 동작만 조금 다른 경우라 그대로 두었습니다.
- **문자열 대신 enum을 쓴 이유 (컴파일 검사, 오타 방지 등):** 작성자 보완

### 9.4. `SequenceEqual` → `for` 비교 (작성자 보완)

- **기록된 것:** `notes/S4.md` 47행 "LINQ `SequenceEqual` → 직접 비교 루프"뿐입니다. 스타일 가이드가 LINQ를 쓰지 않는 문법으로 정해 두었으므로 규칙을 적용한 것은 확실합니다.
- **이유:** 작성자 보완. 매 입력마다 호출되는 비교라 LINQ 할당을 피하려 했을 수 있지만, 확인된 근거는 없습니다.

### 9.5. 저장 방식: JSON 파일 (원본 확인)

- **원본의 저장 방식:** 원본(`bf227ba`)의 `SaveManager`는 `JsonUtility.ToJson`으로 직렬화해 `File.WriteAllText`로 파일에 저장하고, `File.ReadAllText`와 `JsonUtility.FromJson<SaveList>`로 불러옵니다. `PlayerPrefs`는 원본에서 한 번도 쓰지 않았습니다 (`git grep` 결과 Unity 엔진 DLL만 나옴).
- **유지한 것:** 저장 형식(JSON)과 `SaveList` 필드 이름은 1·2차 모두 그대로 두어, 기존 세이브 파일을 읽을 수 있게 했습니다 (5.1.3.5).
- **2차에서 바꾼 것:** 저장 위치만 `Application.dataPath/Save`에서 `Application.persistentDataPath/Save`로 옮겼습니다. 빌드에서 `dataPath`는 설치 폴더(`Wit dream_Data`)라서, 쓰기 권한이 없는 곳에 설치하면 저장이 조용히 실패하기 때문입니다 (plan-2nd R6). 예전 파일이 있으면 처음 실행 때 복사합니다 (8.4).
- **PlayerPrefs와의 비교:** 이 프로젝트에는 해당하지 않습니다. 비교한다면 대상은 "JSON 파일 저장"이고, 이유는 작성자 보완입니다.
